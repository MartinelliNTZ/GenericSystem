Um núcleo, dezessete pluginsAETHERIS TOOLBOX

O SISTEMA (00) é o esqueleto: ele cria a aplicação, registra as ferramentas no ToolRegistry e abre cada uma no workspace certo. Cada plugin é uma caixa fechada: recebe os dados que o usuário informa, roda a sua tarefa e devolve um resultado (arquivo, mapa, base ou documento). Por dentro, cada plugin tem as suas subdivisões numeradas (00.1, 01.1, …): N.0 é o plugin em si (a UI) e N.1, N.2… são os módulos internos — service, workers, modelo.

Todo plugin cabe no mesmo movimento. O SISTEMA entrega a ferramenta já montada (página, logger, preferências); o plugin só cuida da sua tarefa e devolve algo para o usuário.

Entradas

  • Arquivos que o usuário seleciona (planilhas, PDFs, imagens, vetores, LAS/KML)
  • A pasta-mãe e a OS (estrutura de projetos)
  • As preferências salvas por ToolKey
  • O projeto ativo (.mtl) e a base de OS (Firebase)

O plugin

  • Herdado de BasePlugin: self.logger, self.preferences, self.page
  • UI montada em _build_ui() com widgets de resources/widgets/
  • Lógica no service e trabalho pesado em workers (QThread)
  • Comunica-se só por sinais do SignalManager — nunca importa outro plugin

Saídas

  • Arquivos convertidos / renomeados / ícones
  • Shapes de limites e zonas na base e no projeto
  • Estrutura de pastas padronizada + changelog Word
  • Base de OS atualizada (Firebase + backup JSON)
  • Mapa navegável, logs e console

O SISTEMA (00): o esqueleto que sustenta tudo

Antes de qualquer plugin existir, o núcleo precisa estar de pé. Ele cria a aplicação, registra as ferramentas, monta menus e workspaces, e oferece os serviços que todo plugin usa de graça. Nada de regra de negócio mora aqui — só o alicerce.

Como um plugin nasce

Um plugin existe em quatro passos, todos fora dele:

1. ToolKey · a chave única (core/enum/ToolKey.py)
2. Plugin · classe em plugins/<pasta>/<Nome>Plugin.py
3. ToolRegistry · entrada em _TOOLS com _make_factory
4. ToolType / CategoryTool · onde aparece na toolbar

O registro é lazy: o widget só é instanciado quando a ferramenta é aberta.

Três áreas de trabalho

  • CENTRAL — abas no topo (a maioria das ferramentas)
  • LEFT_SIDE — painel esquerdo fixo (Explorador)
  • RIGHT_SIDE — painel direito fixo (Console)
  • BOTH — pode ir para o central ou qualquer lado
  • INSTANT — não abre aba: executa e se auto-destrói

O WorkspaceManager decide onde cada uma abre; a MainWindow nunca mexe nos workspaces direto (Contratos 14 e 16).

O que o BasePlugin entrega

  • self.logger — LogUtils já com tool_key e classe
  • self.preferences — preferências do plugin carregadas do disco
  • self.sys_preferences — seção System (opcional via sys_prefs=True)
  • self.page — PluginPage com título, badge e buttons_config
  • self.main_layout — layout pronto para addWidget
  • self.statistics — monitor de tempo/ETA

Sinais em vez de imports

Nenhum plugin conhece outro (Contrato 7). Tudo passa pelo SignalManager:

tool_openedproject_changedconsole_messageexecution_startedexecution_finishedprogresshud_showhud_hide

É assim que o Explorador sabe que o projeto mudou, e o Console sabe o que escrever.

Cada plugin, um por um

Os plugins não têm ordem: clique em qualquer quadrado para ver o que ele precisa, o que entrega e as subdivisões internas — N.0 é o próprio plugin (entry point / UI) e N.1, N.2… são as partes internas; a 00 mostra o próprio sistema. Cada quadrado traz o número, o nome, o grupo na toolbar (ToolType) e onde a ferramenta abre (CategoryTool).

Padronizações que mantêm tudo coerente

Poucas regras, aplicadas sempre. É por isso que dá para criar, trocar ou testar qualquer plugin isoladamente.

Anatomia de uma pasta de plugin

Um plugin é uma pasta em plugins/ com o plugin e, quando cresce, os seus módulos.

plugins/<nome>/
<Nome>Plugin.py · o entry point (UI + orquestração)
<Nome>Service.py · lógica pura, sem widgets
*Worker.py · trabalho pesado em QThread
model/ · renderers/ · partes específicas
__init__.py · marca o pacote

Ferramentas pequenas são só o plugin — um arquivo.

Widgets reutilizáveis (Contrato 11)

Nada de montar label + campo + botão à mão. Existe um widget para cada peça:

  • PluginPage · a página padrão com título, badge e botões
  • GroupPainel / SectionPanel · painéis com título
  • Grid* · grades (LineEdit, CheckBox, Selector, CardView, Tree…)
  • Simple* · botões, labels, combos e seletores
  • FileListView / FileTreeWidget · arquivos e árvore

Preferências por ferramenta

  • Cada plugin tem a sua seção no config/<APP>_preferences.json
  • Chave = ToolKey da ferramenta (Contrato 26)
  • load_prefs() / save_prefs() são obrigatórios (Contrato 6)
  • Nunca instancie Preferences à mão: use self.preferences
  • O closeEvent persiste automaticamente

Grupos na toolbar (ToolType)

A toolbar agrupa os botões por tipo visual — a cor e o agrupamento vêm daqui:

SystemLayoutsFolderVectorAgricultureRasterImagePointsVerra

O MenuManager lê o ToolRegistry e monta um ToolGroup por tipo.

Subdivisões numeradas

Cada plugin é uma caixa fechada por fora e numerada por dentro: N.0 é o plugin (entry point), N.1, N.2… são as partes internas.

  • N.0 monta a UI, lê as preferências e chama o service
  • A regra de negócio mora no service, não no plugin
  • Trabalho pesado vai para workers — a UI nunca trava
  • Parte comum a dois plugins sobe para utils/ ou core/

Feedback padronizado

  • Progresso no Console e na ProgressBar central via sinais
  • HUD (HudCircularRingsLoader) para operações longas
  • MessageBox de utils.MessageBox — nunca QMessageBox (Contrato 1)
  • Sucesso com stats_message() / output_message()
